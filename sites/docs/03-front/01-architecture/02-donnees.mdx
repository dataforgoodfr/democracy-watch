## Le parcours d'une page

<Mermaid
  chart={`sequenceDiagram
  autonumber
  actor U as Utilisateur
  participant R as Route Next.js<br/>(sites/web/app)
  participant V as Écran<br/>(packages/screens)
  participant Q as Hook TanStack Query<br/>(packages/api)
  participant D as Repository<br/>(mock ou HTTP)
  U->>R: GET /recherche?q=pesticides&etape=commission
  R->>V: <SearchScreen params={searchParams} />
  V->>V: parseSearchParams → filtres typés (+ textes suivis du store)
  V->>Q: useSearch(filtres)
  Q->>D: repository.search(filtres)
  D-->>Q: résultats (mis en cache par clé de requête)
  Q-->>V: chargement → données (ou erreur + « Réessayer »)
  U->>V: coche « Dépôt »
  V->>R: navigate("/recherche?…&etape=depot") — nouvelle clé, nouvelle requête`}
/>

- **Les écrans chargent leurs données côté client**, avec TanStack Query : états de chargement
  (`LoadingState`) et d'erreur (`ErrorState`) systématiques, cache par clé (`queryKeys`).
- **Toute interaction de filtre se traduit par une nouvelle URL** ; la clé de requête change et
  les résultats précédents restent affichés pendant le rechargement.

## Mode DEV_FRONT : le front sans API

| `NEXT_PUBLIC_API_MODE` | Source des données | Usage |
| --- | --- | --- |
| `DEV_FRONT` | `createMockRepository()` : données fictives des maquettes, délai réseau simulé (300 ms) | développement, démo V0, tests e2e |
| `API` | `createHttpRepository({ baseUrl: NEXT_PUBLIC_API_URL })` : API FastAPI | dès que l'API est déployée |

Le mode est fixé **au build** (`sites/web/.env.development`, `.env.production`, ou variables
d'environnement). Les deux dépôts respectent la même interface `Repository` et appliquent les
mêmes requêtes pures (`packages/data`) : les écrans ne voient pas la différence.

```bash
pnpm dev                                                    # DEV_FRONT (par défaut)
NEXT_PUBLIC_API_MODE=API NEXT_PUBLIC_API_URL=http://localhost:8000 pnpm dev   # API locale
```

## L'état du navigateur

Ce qui appartient à l'utilisateur, et non aux données, est gardé dans le navigateur avec
**Zustand** (`packages/state`) :

| Store | Contenu | Stockage |
| --- | --- | --- |
| `useFollowStore` | textes suivis + préférences (articles à suivre, alertes, thématique) | `localStorage` — clé `dw:suivi` |
| `useSessionStore` | session de démonstration (e-mail) | `sessionStorage`, ou `localStorage` si « Rester connecté » — clé `dw:session` |

Les stores sont relus **après le premier rendu** (`rehydrateStores`, appelé par les `Providers`) :
le rendu serveur et le premier rendu client sont identiques, sans erreur d'hydratation.
`useStoresHydrated()` indique quand l'état est disponible.

L'état éphémère d'une page (la sélection en cours dans « Ajouter des textes ») reste dans le
composant ; l'état partageable (filtres, onglet, vue, page) reste dans l'URL :

| Écran | Paramètres d'URL |
| --- | --- |
| Recherche | `q`, `type` (textes, articles, amendements), `suivis=1`, `etape`, `commission`, `groupe`, `depuis` |
| Ajouter des textes | `q`, `type` (PJL, PPL…), `encours=0`, `page` |
| Article | `q`, `vue` (liste, groupe), `similaires=1` |
| Amendements suivis | `q`, `texte`, `groupe`, `statut`, `etape` |
| Connexion | `suite` (page à rouvrir après connexion, chemin interne uniquement) |

Les types sont dans `packages/data/src/types.ts` ; le vocabulaire est expliqué dans
[Notions métier](/produit/notions-metier). L'interface `Repository` est le seul point d'accès
aux données pour les écrans :

```ts
export type Repository = {
  search(filters: SearchFilters): Promise<SearchResults>;
  listTexts(filters: TextCatalogFilters): Promise<Page<LegislativeText>>;
  getTexts(ids: string[]): Promise<LegislativeText[]>;
  getText(id: string): Promise<LegislativeText | null>;
  listArticles(textId: string): Promise<ArticleSummary[]>;
  getArticleView(textId: string, articleNumber: string): Promise<ArticleView | null>;
  listAmendments(filters: AmendmentFilters): Promise<AmendmentResult[]>; // filters.scope = textes suivis
  listCommissions(): Promise<Commission[]>;
  referenceDate(): string; // date des échéances « J-n »
};
```

Deux implémentations : `createMockRepository()` (données fictives, mode DEV_FRONT) et
`createHttpRepository()` (API FastAPI). Le choix se fait dans `sites/web/lib/api.ts`.

## Connexion

### V0 (7 novembre)

Pas d'authentification réelle. `/connexion` ouvre une **session de démonstration** (l'e-mail est
retenu, le mot de passe n'est pas vérifié) ; « Rester connecté » la garde dans `localStorage`,
sinon elle disparaît à la fermeture de l'onglet. Toutes les pages de l'application exigent une
session : sans elle, `AppLayout` renvoie vers `/connexion?suite=<page demandée>`.

<Mermaid
  chart={`sequenceDiagram
  autonumber
  actor U as Utilisateur
  participant L as AppLayout
  participant C as LoginScreen
  participant S as useSessionStore
  U->>L: /textes
  L->>S: session ?
  S-->>L: aucune
  L->>C: /connexion?suite=/textes
  U->>C: e-mail, mot de passe, « Rester connecté »
  C->>S: signIn(email, remember)
  S-->>S: localStorage ou sessionStorage
  C->>L: retour à /textes`}
/>

### Cible

<Mermaid
  chart={`sequenceDiagram
  autonumber
  actor U as Utilisateur
  participant W as sites/web
  participant A as API (server/)
  participant M as E-mail
  U->>W: /connexion — saisit son e-mail
  W->>A: POST /auth/lien-magique
  A->>M: envoie un lien à usage unique (15 min)
  U->>W: clique le lien /auth/verifier?jeton=…
  W->>A: vérifie le jeton
  A-->>W: session (cookie httpOnly)
  W-->>U: redirige vers la page demandée
  Note over W,A: Textes suivis et préférences passent alors du navigateur au serveur (par organisation)`}
/>

Mot de passe et lien magique coexistent. L'inscription crée un compte rattaché à une
**organisation** (association, ONG), qui porte les textes suivis et les thématiques.
